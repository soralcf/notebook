# 第一课：软件构造与复杂度

对应阅读：《Code Complete, 2nd Edition》第 1 章。第一次学习只需要阅读这一章，不必提前追赶后续内容。

## 这一课要解决什么

很多人把“写代码”理解为把已经明确的设计翻译成编程语言。但真实项目里，类如何分解、函数承担什么职责、错误怎样表达、数据由谁拥有等决定，往往要在构造过程中完成。

因此，软件构造（software construction）不只是输入语法，而是在需求与架构约束下，通过详细设计、编码、验证、调试和集成，持续制造可以运行、理解和修改的软件。

完成这一课后，应当能够：

- 用自己的语言解释软件构造的范围；
- 区分构造问题、需求问题和架构问题；
- 从一段真实代码中识别业务本身的复杂度与代码额外引入的复杂度；
- 为后续改造选出一个可观察、可验证的起点。

## 核心模型：构造是在控制复杂度

复杂业务不会因为代码整洁而消失。例如，支付可能存在授权、扣款、退款和失败恢复等真实状态。这类来自问题本身、无法随意删除的困难，可以称为本质复杂度（essential complexity）。

另一类困难是实现额外制造的：名称无法表达含义、共享状态来源不明、一次修改要跨越许多文件、控制流需要在脑中反复模拟。这些可以称为偶然复杂度（accidental complexity）。

软件构造的一个核心任务，是准确表达不可避免的复杂度，同时避免让实现再增加不必要的认知负担。

```text
业务规则与外部约束
        ↓
不可避免的复杂度
        ↓
构造决定：类型、接口、数据、控制流、错误处理
        ↓
读者实际需要承担的理解成本
```

“代码短”“函数少”或“使用了某种模式”都不能单独证明复杂度更低。更有用的问题是：完成一次修改需要理解多少无关信息？一个错误会在哪个边界被发现？代码是否让重要规则直接可见？

## 与相邻活动的边界

这些活动会相互影响，但观察层级不同：

- **需求（requirements）**关心系统应当满足哪些用户目标和约束；
- **架构（architecture）**关心系统级边界、关键质量目标以及高成本决定；
- **软件构造（software construction）**关心怎样把这些约束落实为类、函数、数据、控制流、错误处理和可执行反馈；
- **编程（programming）**常被宽泛地使用，也可能只指语言和编码活动，需要结合语境判断。

构造无法补救所有上游问题。如果关键业务规则相互矛盾，增加更多条件分支只会隐藏需求缺口。如果跨服务的数据所有权没有确定，局部封装也无法消除系统级冲突。识别问题属于哪一层，本身就是构造判断的一部分。

## 第一组英文术语

| 术语 | 在本课程中的含义 |
| --- | --- |
| `software construction` | 从详细设计到编码、验证、调试和集成的一组实现活动 |
| `upstream prerequisites` | 进入构造前需要具备的需求、架构和环境条件 |
| `detailed design` | 落到类、函数、数据、接口和控制流层面的设计 |
| `routine` | 对 function、method、procedure 等可调用单元的统称 |
| `manage complexity` | 让必要复杂度可理解，并减少实现额外引入的复杂度 |

阅读时先根据上下文理解这些词所承担的工程含义，不需要寻找唯一的中文译法。

## 阅读前练习

不要查书，先在自己的学习笔记中回答：

1. 我认为 software construction 包括哪些活动？
2. 它和 architecture、programming 分别有什么区别？
3. 我最近遇到的一个“代码很难改”的例子是什么？
4. 困难来自业务本身，还是实现额外引入的复杂度？依据是什么？

这里没有要求一次答对。阅读后的变化比初始答案本身更重要。

## 阅读任务

阅读第 1 章时，只追踪以下三个问题：

1. 作者怎样界定 construction 在软件开发中的位置？
2. 为什么构造质量会持续影响后续测试、维护和修改成本？
3. 哪些决定虽然发生在编码期间，本质上属于详细设计？

最多记录五个工程主张。不要摘抄完整段落；每条先用自己的中文重新表达，再记下对应的英文关键词或页码，方便回查。

## 代码观察练习

从最近写过或维护过的代码中选择一个 20–80 行的函数。暂时不要重构，只完成观察记录：

```markdown
## 观察对象

- 函数及所在位置：
- 它对调用者承诺的结果：
- 显式输入与输出：
- 隐藏依赖或共享状态：
- 必须始终成立的不变量：
- 错误处理策略：
- 最可能发生变化的位置：
- 阅读者必须同时记住的事实：

## 初步判断

- 哪些复杂度来自问题本身？
- 哪些复杂度是当前实现引入的？
- 我目前有什么证据支持这个判断？
```

不要仅凭函数行数判断好坏。需要观察它的调用关系、状态来源和外部可见行为。

## 闭卷复盘

合上书和笔记，用自己的语言回答：

1. 为什么 software construction 不等于输入代码？
2. 如何区分 essential complexity 与 accidental complexity？
3. 举出一个不应该只在局部代码中修补的上游问题。
4. 选择代码观察练习中的一个构造决定，说明可以怎样验证它是否改善了代码。

## 完成标准

满足下面条件后再进入下一课：

- 阅读前问题和阅读后答案都已保留，可以看到理解发生了什么变化；
- 能够不看书解释 `software construction`、`detailed design` 和 `manage complexity`；
- 已完成一个真实函数的观察记录；
- 至少指出一项本质复杂度和一项实现引入的复杂度；
- 为后续修改提出了一个可以通过测试、静态检查或明确观察验证的假设。

下一课将进入软件隐喻（software metaphors）：隐喻如何影响我们理解设计活动，以及为什么任何单一隐喻都会遮蔽一部分现实。
