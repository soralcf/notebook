# 《Code Complete, 2nd Edition》系统学习指引

这份指引以 Steve McConnell 的英文版《Code Complete, 2nd Edition》为主教材，目标不是尽快读完一本大书，而是逐步建立可以落实到代码、测试、评审和工程决策中的软件构造能力。

书中的代码示例和部分工具背景来自 2004 年。学习时应保留它对复杂度、详细设计、质量反馈和工程纪律的讨论，同时用当前使用的编程语言、测试框架、静态分析工具和性能测量方法重新验证具体做法。

## 学习目标

完成这条路线后，应当能够：

- 解释软件构造（software construction）与需求、架构、编程语法之间的关系；
- 从命名、作用域、类型、控制流、接口和依赖中识别额外复杂度；
- 设计职责清楚的类、函数和数据结构，并说明其边界与代价；
- 使用防御式编程、测试、调试和重构建立短反馈环；
- 先测量再优化，并用可重复的证据评价改动；
- 在代码评审和个人实践中形成可执行、可修订的构造准则。

## 学习路线

路线保留原书从局部构造走向系统实践的总体方向，但按可验证的能力组织学习，不把章节阅读本身当作完成标准。

| 阶段 | 对应阅读 | 核心问题 | 完成证据 |
| --- | --- | --- | --- |
| 1. 建立构造视角 | 第 1–4 章 | 编码开始前需要明确什么？构造决策怎样受需求、架构、语言和项目环境约束？ | 一份构造决策记录 |
| 2. 控制局部复杂度 | 第 5–9 章 | 类、函数、防御式检查和伪代码怎样降低同时需要理解的信息量？ | 一个带自动化测试的小功能 |
| 3. 让数据表达意图 | 第 10–13 章 | 变量作用域、生命周期、命名、类型和共享状态怎样影响推理成本？ | 一次数据表达重构及说明 |
| 4. 让控制流显式 | 第 14–19 章 | 怎样暴露执行依赖并简化条件、循环、嵌套和特殊控制结构？ | 一组控制流改造前后对比 |
| 5. 建立质量反馈环 | 第 20–24 章 | 评审、测试、调试和重构如何协同发现并防止缺陷？ | 缺陷记录、回归测试和安全重构 |
| 6. 用测量指导性能 | 第 25–26 章 | 怎样区分性能猜测、系统级瓶颈和值得实施的代码优化？ | 可重复的基准测试与优化报告 |
| 7. 形成工程实践 | 第 27–35 章 | 规模、集成、工具、代码表达和个人习惯怎样共同影响构造质量？ | 最终代码审查与个人构造清单 |

## 每个学习单元的闭环

每章或每个主题都采用同一条反馈路径：

```text
预览问题
   ↓
阅读核心材料
   ↓
用自己的语言解释
   ↓
在代码中应用
   ↓
用测试或测量验证
   ↓
闭卷复盘
```

具体做法：

1. **Preview**：先看标题、小节和检查清单，预测作者试图解决的问题。
2. **Read**：阅读英文原文，只记录三到五个重要工程主张。
3. **Explain**：用中文重新解释，第一次出现时保留关键英文术语。
4. **Apply**：把其中一个主张应用到真实代码或专门练习。
5. **Verify**：用测试、静态检查、复杂度变化、评审结果或 benchmark 提供证据。
6. **Retrieve**：合上书回答三个问题：它解决什么、何时适用、代价是什么。

推荐使用下面的笔记模板：

```markdown
## Concept

### Essence
它解决什么问题？

### Mechanism
它通过什么机制起作用？

### Trade-offs
什么时候有效？会付出什么代价？

### Evidence
我在代码、测试或测量中观察到了什么？

### Retrieval
不看书，我能否重新解释和应用它？
```

## 怎样阅读英文原版

- 不逐句翻译。先判断一段文字在提出问题、给出经验规则、说明证据，还是讨论例外。
- 只记录具有工程含义的词汇，例如 `construction`、`routine`、`defensive programming` 和 `upstream prerequisites`。
- 遇到旧语言示例时，先还原它要控制的风险，再用当前语言表达同一决定。
- 对带有数字、经验统计或工具假设的结论，记录其适用背景，不直接推广到当前项目。
- 章末检查清单用于评审真实代码，不作为背诵题库。

## 关于示例代码

练习优先使用自己熟悉的语言。关注的是构造决定以及改动证据，不要求复刻书中的 C++、Java 或 Visual Basic 示例。每次练习应尽量保留：

- 改动前的行为或问题描述；
- 改动后的代码；
- 自动化测试或可重复的观察步骤；
- 为什么这样修改，以及什么情况下不应这样修改。
